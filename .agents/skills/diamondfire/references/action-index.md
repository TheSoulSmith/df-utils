## 2. Naming rules that affect generated templates

1. **Exact strings.** The wire `action` of a block is the dump `name` byte-for-byte. 38 names have leading/trailing spaces (e.g. `" RoundNumber "`, `" SetBlock "`, `" Range "`). Never trim them. Generated docs show such names in double quotes.
2. **Padded twin = current, plain twin = legacy.** 174 actions carry `legacyReplacement`. In 29 of the 35 same-block padded/plain pairs the padded name is current and the plain one is legacy, and the legacy entry's `legacyReplacement.action` is the padded name. Always emit the replacement, never the legacy action. (4 pairs have two current twins; 2 pairs are odd — each doc entry carries its own LEGACY flag, trust that.)
3. **Aliases.** `aliases` are alternative search names. **Exception that matters for the wire format:** for the 19 `if_*` actions whose name collides across if-blocks (`IsNear`, `NameEquals`, `StandingOn`, …) the dump's `subAction` is empty and the **alias is the identifier** used in `subAction` of `select_obj`/`repeat` blocks and in tag `action` fields. Verified: sample uses `PIsNear`, `EIsNear` (aliases of `IsNear` in `if_player`/`if_entity`); `ListContains` is unique so it needs no alias. Alias pattern: `P`/`E`/`V`/`G` + name for player/entity/var/game, with exceptions (e.g. `HasPotion` in `if_player` has alias `HasEffect`; `IsHitboxNear` → `PHitboxIsNear`). Use the alias listed on each entry.
4. **Game value / particle / potion / sound identifiers.** Game values: display name with `\u00a7` colour codes removed. Particles, potions, sounds (item version 1): `minecraft:` + id from the dump.

## 3. Argument ↔ slot rules (checked against 5 sample templates)

```
canonical layout:  chest slot n  <-  the n-th typed argument in the entry's Args list (plural args absorb following slots)
tags:              right-aligned at the end of the chest; slot numbers are stated on each tag (26 first, then 25, 24, ...)
```
Test result: of 219 sample items (excluding variables/game values, which can sit in any typed slot), **214 sit exactly at slot == argument index**. The other 5 are all the same phenomenon: an *optional* argument was omitted and the editor **compacted** the items (`ShiftOnAxis` number in slot 1 instead of 2; `repeat Multiple` amount in slot 0 instead of 1). So DF matches chest items to arguments in order **and by type**; compaction is accepted when the remaining items are unambiguous by type. **When adjacent optional arguments have the same type (e.g. `SetAllCoords` X/Y/Z/Pitch/Yaw), leave real gaps** — position is the only way to say which one you mean.
`OR` rows in an Args list separate alternative argument sets. **Verified** (sample 20, `if_player StandingOn` = `BLOCK` OR `LOCATION`): when the `OR` group starts the argument list, **each alternative is filled starting at slot 0**. Unverified: groups where an argument precedes the `OR` (e.g. a leading `VARIABLE`).
